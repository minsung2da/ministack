    DDB-01 — Tables list / create / delete (steps 1-5)
    ----------------------------------------------------------------

      1. Click "DynamoDB" in the sidebar → URL becomes `/_console/services/ddb`; page heading reads "DynamoDB"; an empty table list with "Create table" button is visible.

      2. Click "Create table" → modal opens. Enter:

         - Partition key name: `pk`, Partition key type: `S` (String)
         - No sort key
         Submit → modal closes; Flashbar success `Table {name} created successfully.`; new row appears in the list with KeySchema `pk (S)`.

      3. Click "Create table" again → modal opens. Enter:
         - Table name: `phase5-pk-sk-$(date +%s)`
         - Partition key name: `pk`, type `S`
         - Sort key name: `sk`, type `N` (Number)
         Submit → modal closes; Flashbar success; new row appears with KeySchema showing both `pk (S)` and `sk (N)`.

      4. Click the PK+SK table's name link → URL becomes `/_console/services/ddb/{name}`; detail page heading shows table name; KeySchema section reiterates `pk (S)` HASH + `sk (N)` RANGE.

      5. From the detail page, click Actions → Delete → modal prompts "Type table name to confirm". Type a wrong name → Delete button disabled. Type the exact table name → Delete enabled. Confirm → Flashbar success; URL redirects back to `/services/ddb`; the deleted table is gone from the list. Verify via CLI:
         ```
         aws --endpoint-url http://localhost:4566 dynamodb describe-table --table-name {deleted-name}
         ```
         returns `ResourceNotFoundException` (the table is actually gone — not just hidden from the UI).

    ----------------------------------------------------------------
    DDB-02 — Scan, filter, pagination, SplitPanel detail (steps 6-10)
    ----------------------------------------------------------------

      6. Navigate back to the remaining PK-only table detail. Items tab shows empty state (0 items displayed).

      7. Seed 15 items via CLI (run once):
         ```bash
         TBL=phase5-pk-only-NAME   # substitute the real table name from step 2
         for i in $(seq 1 15); do
           STATUS=$([ $((i % 2)) -eq 0 ] && echo pending || echo done)
           aws --endpoint-url http://localhost:4566 dynamodb put-item \
             --table-name "$TBL" \
             --item "{\"pk\":{\"S\":\"$i\"}, \"status\":{\"S\":\"$STATUS\"}}"
         done
         ```
         Refresh the detail page → click Scan → item count rises to 15 (first page may show 10 per default page size; see step 9 for pagination).

      8. Enter a FilterExpression in the Scan form:
         - FilterExpression: `#s = :s`
         - ExpressionAttributeNames: `{"#s":"status"}`
         - ExpressionAttributeValues: `{":s":{"S":"pending"}}`
         (The form per D-03 exposes these three inputs — or a single JSON-mode pane. Either path is acceptable.)
         Click Scan → the rendered rows are only the `status=pending` items (roughly 7 of the 15 seeded).

      9. Clear the filter and re-Scan with page size 10 (default). Page 1 shows 10 rows, a `Next page` button is enabled (driven by `LastEvaluatedKey`). Click `Next page` → page 2 shows the remaining 5 rows. Click `Previous` or reset → returns to page 1. Pitfall parity with Phase 3 prefix navigation: changing the filter after paginating MUST reset to page 1 (start token cleared).

      10. Click any item row → SplitPanel opens at the bottom showing the raw DDB JSON for that item (e.g. `{"pk":{"S":"7"},"status":{"S":"done"}}`). Confirm no JSON fields are silently hidden — all attributes present in the stored item are visible.

    ----------------------------------------------------------------
    DDB-03 — Item CRUD (PutItem / UpdateItem / DeleteItem) with D-06 scalars + D-03 JSON mode (steps 11-15)
    ----------------------------------------------------------------

      11. Click "Create item" on the same table. The schema-based form per D-03 renders:
          - `pk` (required, type S — text input, inline validation on empty)
          - An "Add attribute" control lets you append fields, each with a type selector covering D-06's five types: S, N, B, BOOL, NULL.
          Add one of each type (e.g. `name=alice` S, `count=42` N, `blob=SGVsbG8=` B (base64), `flag=true` BOOL, `placeholder` NULL). Fill `pk=scalar-demo`. Submit → Flashbar success; scan the table → the new item appears with all five attributes present and correctly typed.

      12. Click "Create item" again. Toggle to JSON mode (per D-03). Paste a complex item using List `L` and Map `M` (not supported in form mode per D-06):
          ```json
          {
            "pk": {"S": "complex-demo"},
            "tags": {"L": [{"S": "a"}, {"S": "b"}]},
            "meta": {"M": {"v": {"N": "1"}, "active": {"BOOL": true}}}
          }
          ```
          Submit → Flashbar success. Scan → row present; row click in SplitPanel shows the L/M preserved verbatim.

      13. Open the `scalar-demo` item detail → click Edit → modify `count` from `42` to `99` (UpdateItem path) → Save → Flashbar success; scan table and re-open the item → `count` now shows `99`.

      14. On the `scalar-demo` item, click Delete → modal prompts for type-to-confirm by the composite key (here only `pk=scalar-demo` since no sort key). Type wrong → disabled. Type `scalar-demo` → enabled. Confirm → Flashbar success; scan → row gone. Verify via CLI:
          ```
          aws --endpoint-url http://localhost:4566 dynamodb get-item \
            --table-name "$TBL" --key '{"pk":{"S":"scalar-demo"}}'
          ```
          returns no `Item` (empty response).

      15. Open "Create item" once more. Leave `pk` empty → inline FormField errorText "Partition key is required" appears; Submit button disabled. Fill `pk` but paste invalid JSON in JSON mode → errorText "Invalid JSON: ..." appears; Submit disabled. Cancel without saving.

    SQS-02 — SendMessage / manual Poll / accumulating list / DeleteMessage (steps 19-23)
    ----------------------------------------------------------------

      19. Create a new queue (re-run step 17 flow). Click the queue name link → detail page with `Poll` button visible. Click Send message → SendMessageModal opens. Enter:
          - Body: `hello-1`

      20. Back on the queue detail, click the `Poll` button (D-04 — manual, not auto). The receive call runs ONCE. One or both messages appear in the messages list with: `MessageId`, `ApproximateReceiveCount` (= 1), Body (`hello-1` or `hello-2`), and the two MessageAttributes rendered (e.g. `source: manual`, `priority: 5`).

      21. Wait past the visibility timeout (default 30s in backend) OR open another queue's messages to confirm the accumulating semantic:
          - Click `Poll` a second time. New receive results APPEND to the running list (not replace). If the same MessageId shows up again (visibility timeout expired) its `ApproximateReceiveCount` is now `2`. Confirm previously received rows are STILL visible above the new ones — they were not wiped by the second Poll (D-04 accumulating list guarantee).

      22. On any message row, click Delete → the call uses the ReceiptHandle (not the MessageId). The chosen message disappears from the list; other messages remain intact. Poll again → the deleted message no longer returns from the backend even after visibility timeout. Verify via CLI:
          ```
          aws --endpoint-url http://localhost:4566 sqs get-queue-attributes \
            --queue-url <url> --attribute-names ApproximateNumberOfMessages
          ```
          count decreased by one.
